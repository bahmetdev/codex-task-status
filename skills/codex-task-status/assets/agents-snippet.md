## Task titles

Initial naming is the one exception to suffix-only updates: at a new task's first
substantive turn (including consultation), read its live title and initialize
the approved subject plus truthful state once. An automatic app title is not
a user choice just because it exists; preserve explicit names or evidenced UI
renames. After verified initialization, only status changes automatically.
Never reinitialize on resume, restart, compaction, or later prompts. Preserve
established titles with uncertain history; no new naming registry is needed.

Use the installed `codex-task-status` skill when substantive work begins or resumes and before finalizing it. Use the recommended `<Subject> (<state>)` structure unless a custom policy is recorded below. Keep the subject stable unless the user renames it: a UI or explicitly requested rename becomes the new canonical subject, even if it has multiple words or another language. Before every suffix write, reread the live title and preserve the exact subject; never restore a cached name or normalize a user choice. Replace only a recognized trailing status/schedule, preserving other parentheses; skip the write if the current title is unavailable. Update only a stale suffix on a meaningful evidence-backed transition. Use available task-title controls and verify the result, or propose the title if controls are unavailable. Do not rename on every message or tool call. Routine recurring runs retain their verified schedule suffix. Preserve archived and other tasks unless explicitly asked to change them.

Custom policy, if selected: record the subject language/shape, title format, status labels mapped to their meanings, transition rules, Git/non-Git behavior, and schedule notation here or link a durable policy file. Syntax validation JSON alone is not the semantic policy.
